Phase 1
Workflow Authoring (Design & Canvas Editor)
👤 Publisher in 💻 Visual Studio
  • 1 Publisher initializes a new local project or pulls a draft revision from Cloud Sync.
  • 2 Drag action nodes from catalog (Tap, Swipe, Input Text, Wait Element, Condition, Loop Controller,...).
  • 3 Schema Form Renderer automatically synthesizes typed parameter input forms driven by NodeDefinition.
  • 4 Define workflow variables and bind execution parameter profiles (Input Profiles).
Core Invariant: Arbitrary graph looping is strictly prohibited. All cyclical logic must reside within a Loop Controller container bounded by an explicit maxIterations parameter.
Phase 2
Local Verification & Execution (Dev Mode Testing)
👤 Publisher ── ⚙️ Runtime ── 📱 Android Device
  • 1 Visual Studio queries local daemon (127.0.0.1:<port>) to discover instances via ldconsole list2 and adb devices -l.
  • 2 Publisher selects target emulator and test scope: Run All, Run From Node, or Single Node.
  • 3 Visual Studio compiles the canvas into an in-memory Runtime IR and transmits it to Runtime with an ephemeral Dev Mode session token.
  • 4 Runtime acquires an Exclusive Device Lock on the emulator to prevent conflicting control.
  • 5 Runtime streams step-by-step logs and screen dumps back via WebSocket to highlight active nodes on the canvas.
"Dispatched vs Confirmed" Principle: Successful ADB command dispatch only implies Dispatched. A node is only Confirmed upon successful screen validation (e.g., Wait Element / image template match).
Phase 3
Revision Freezing & Cloud Synchronization
💻 Visual Studio ── ☁️ Backend
  • 1 Publisher clicks "Prepare to Publish" in Visual Studio.
  • 2 Visual Studio executes comprehensive linter checks: Verifies zero orphaned ports, complete terminal branches, and packaged template assets.
  • 3 Visual Studio bundles IR graph and template assets, uploading the bundle to Backend.
  • 4 Backend persists an immutable Workflow Revision record (Snapshot identifier rev_...).
Anti Bait-and-Switch Protection: Once frozen, a Revision cannot be modified. Any subsequent graph edits in Studio create an entirely new Draft Revision.
Phase 4
Listing Registration & Automated Security Scanning
👤 Publisher ── ☁️ Backend
  • 1 Publisher accesses Web Marketplace Portal, selecting the target frozen revision.
  • 2 Defines commercial metadata (ProductListing): Title, detailed description, media screenshots, compatible resolution, and Coin Price.
  • 3 Publisher submits the form → Backend creates an official Submission entity.
  • 4 Task enqueued to Redis for Automated Scanner: Analyzes static AST/IR, detects shell injection, destructive ADB command patterns, and declares device capabilities.
Automated Safety Gate: If malicious patterns are detected, the system immediately tags REJECTED_AUTOMATED with diagnostics, sparing Admin review overhead.
Phase 5
Administrative Moderation & Release Packaging
🛡️ Admin ── ☁️ Backend
  • 1 Admin opens submission ticket in Moderation Console: Inspects AST IR graph, verifies scan report, and executes in isolated sandbox if required.
  • 2 Admin Decision: If rejected → Enter formal feedback reason. If approved → Trigger automated packaging worker.
  • 3 Packaging Worker: Bundles IR and assets into a standardized .a2m package.
  • 4 Encrypts .a2m package using AES-GCM (with Backend Master Encryption Key) and computes SHA-256 checksum.
  • 5 Uploads package to S3 Object Storage, creates ProductRelease record, and flips listing status to PUBLISHED.
Intellectual Property Security: Plaintext IR is never stored on disk or transmitted unencrypted. At runtime, the package is decrypted strictly in client RAM via an ephemeral Execution Lease.

Failure Handling States: REJECTED_AUTOMATED (Scanner flags malicious IR patterns) or REJECTED_ADMIN (Admin rejects submission with policy reasons). Upon rejection, the submission is permanently closed; the Publisher must branch a new Draft Revision in Studio to re-submit.
